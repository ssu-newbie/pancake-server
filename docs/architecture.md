# 구조와 설계 판단

## 바꾼 이유

기존 `pancake_server.py`에는 앱 설정, 요청 모델, API, 파일 입출력이 함께 있었다. 저장 경로도 모듈 전역값이어서 테스트마다 실제 데이터 경로를 교체해야 했다. API 응답과 저장 로직을 독립적으로 살펴보고 임시 데이터로 반복 검증할 수 있도록 책임을 나눴다.

## 요청 처리

`pancake_server.py`가 `create_app()`을 호출한다. 앱 팩토리는 하나의 `JsonStore`를 만들고 라우터에 전달한다. 라우터는 Pydantic 요청 모델로 입력을 받고 저장소를 호출해 기존 형식의 응답을 돌려준다.

| 구성 | 책임 |
| --- | --- |
| `application.py` | 앱과 저장소의 생명주기, CORS, 데이터 경로 |
| `schemas.py` | 요청 필드와 타입 |
| `api.py` | 길이 절단, 조회 순서와 개수, 최고 점수 등 API 동작 |
| `storage.py` | JSON 파일 읽기, 읽기→추가→교체의 잠금 구간 |

저장소 인스턴스의 잠금 하나를 설문과 점수 쓰기에 공유한다. 임시 파일은 기존 파일과 같은 디렉터리에 작성하고 `os.replace`로 교체한다. 읽기는 기존과 같이 잠금 없이 수행한다. 이 구조는 단일 앱 인스턴스·단일 프로세스 기준이다. 같은 경로에 여러 앱이나 워커를 띄우면 잠금이 공유되지 않는다.

## 이번에 유지한 계약

- `uvicorn pancake_server:app`과 저장 파일의 기본 위치·이름
- 다섯 API의 URL, 요청 모델 이름, 응답 키와 상태 코드
- 설문 목록 길이가 다르면 짧은 쪽에 맞춰 저장하는 처리
- 빈 설문은 저장하지 않고 HTTP 200과 `ok: false`를 반환하는 처리
- 최근 주민의 최신순 반환, 기본 100명, 요청 개수의 1~1000 제한
- 음수 점수 허용, 기록이 없을 때 최고 점수 0
- 모든 출처를 허용하는 CORS와 기존 파일 읽기 오류의 빈 목록 처리

읽기 오류 정책은 설문과 점수가 다르다. 설문은 JSON 구문 오류와 OS 오류를, 점수는 모든 `Exception`을 빈 목록으로 처리한다. 이를 통일하면 장애 시 응답이 달라질 수 있어 별도 개선으로 남겼다. 유효한 JSON이더라도 잘못된 데이터 구조는 검증하지 않는다.

## 후속 변경의 기준

입력 검증 강화는 현재 클라이언트가 의존하는 동작을 먼저 확인하고 별도 변경으로 진행한다. 저장소 이전은 기존 JSON을 읽는 이관 절차와 동시 쓰기 검증을 포함한다. 파일 전체 읽기·쓰기, 손상된 파일이 다음 제출에서 새 목록으로 덮어써질 수 있는 점, 여러 프로세스 간 동시 쓰기 문제는 이번 책임 분리만으로 해결되지 않는다.
